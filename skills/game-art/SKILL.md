# game-art —— 遊戲畫面的職能方法

從一個 UE 俯視 ARPG demo 的六個職能研究整理出來（2026-10-20）。**這裡只寫方法與檢查，不替專案做美術決定**：
專案的支柱、色板、門檻寫在專案自己的美術規則書（第 0 節）。網頁小遊戲的「截圖 → 對照 → 修」打磨循環在 game-polish，
畫面上的問題回到這裡找職能的方法。

## 原則

- **先查職能怎麼做，再動手，不憑感覺調。** 美術指導、燈光師、特效師、UI/UX 設計師、技術美術各有自己的工具、流程與可量的檢查；
  照他們的方法做。曾經有一次憑自己的判斷把整個世界去色，結果跟專案研究列出的每一個參考都相反，使用者說「太黑白」。
- **明度先於顏色。** 「Color can't save a bad value design」（Gurney）。
- **可讀性先於好看。** 主角、敵方前搖、掉落要在最忙、最暗的畫面裡讀得出來。
- **同一幀 A/B，在遊戲裡比。** 不用離線示意圖判斷；改前改後同一個種子、同一個鏡頭並排。
- **數字是護欄。** 業界沒有公開數字的門檻標「提案」，對外不說成業界標準。

## 0. 先找專案的美術規則書

- 在專案 CLAUDE.md 或 `docs/` 找美術規則書（art bible、色彩規則書）。有就照它；跟這份技能衝突時以它為準。
- 沒有就照 [art-bible.md](art-bible.md) 的範本建一份。**支柱與色板由使用者拍板**，你提選項與依據，不要自己決定風格。
- 專案有類型的驗收準則就照它。類型是俯視 ARPG 而專案沒有的，從 [references/arpg-aaa-criteria.md](references/arpg-aaa-criteria.md) 挑條目抄進專案的驗收清單。

## 1. 每一輪的流程

1. **找職能**：確認這次動的是哪個職能，讀對應的參考檔（下表）。專案 `docs/` 已經有該職能的研究就一起讀；兩邊都沒涵蓋就先研究（第 5 節）。
2. **量現況**：固定種子與鏡頭，在遊戲內截一組圖，跑第 3 節的檢查，記下數字。
3. **照職能的方法改**：順序照該職能的順序（例如燈光由大到小），一次一個變數。
4. **重拍同一組**：前後並排，比數字。
5. **記進專案的視覺審查文件**（格式見第 4 節）。
6. **交給使用者看實機**，他的一句話就是下一輪的方向。

| 職能 | 參考檔 | 典型症狀 |
|---|---|---|
| 美術指導與配色 | [references/art-direction.md](references/art-direction.md) | 太灰、太黑、沒有焦點、色彩散 |
| 素材顏色統一 | [references/colour-unification.md](references/colour-unification.md) | 混搭素材包顏色不一、寫實角色像貼在風格化場景上 |
| 燈光 | [references/lighting.md](references/lighting.md) | 看不出主光、暗處讀不到、光源太多太貴 |
| 風格化渲染 | [references/stylized-rendering.md](references/stylized-rendering.md) | 後處理風格（水墨、卡通）角色與場景不一致、線條只有輪廓 |
| 特效 | [references/vfx.md](references/vfx.md) | 特效搶戲、看不出判定、暗處看不見 |
| UI/UX | [references/ui-ux.md](references/ui-ux.md) | 字太小、對比不足、回饋慢、顏色散落在程式裡 |
| 類型驗收（俯視 ARPG） | [references/arpg-aaa-criteria.md](references/arpg-aaa-criteria.md) | 「像獨立原型，不像 3A」 |

## 2. 量測工具

用專案自己的工具量。沒有的話，做一個能對截圖算出第 3 節這些數字的工具（明度直方圖、三階明度稿、12 格色相分組、指定區域的相對亮度對比），
放進專案的 `tools/`，在專案 CLAUDE.md 寫一行用法。截圖一律用遊戲實機輸出，不用編輯器視窗或離線合成圖。

**同一格有／無的差異遮罩**：要量「某個東西」（主角、一個特效）時，同一格拍兩張，一張有它、一張沒有，差異的像素就是它的遮罩。
主角對地、特效畫面佔比都用這個量，不靠手圈範圍。踩過的坑：
- 只保留最大的連通區：閒置動作、光池邊緣會留下零星雜點，把外框撐大，上下身的分界就跑掉。
- 藏主角時讓隱藏的網格照樣投影（UE 的 `SetCastHiddenShadow`）：影子算地面，不算主角。
- 「腳下地面」以腳為圓心、用身高定半徑取樣，不要用含武器的外框；長柄武器會把取樣環推到別處。
- 首領戰之類鏡頭會偏移的場景，主角不在畫面中心，要全畫面找。

## 3. 通用檢查

| 檢查 | 怎麼量 | 門檻與來源 |
|---|---|---|
| 明度分組 | 截圖轉三階明度稿（notan），縮到 1/8 看 | 2–3 個大明度群看得出形狀；主角與焦點在最亮群（Gurney） |
| 焦點 | 最亮 5% 像素的位置 | 落在主角、敵方前搖、掉落（提案；D4 的選擇性打光） |
| 主角對地 | 灰階下，主角上身對腳下地面的相對亮度對比 | ≥ 3:1（借 XAG 102 大型元素；Dota 2 角色指南），最亮與最暗的區域都要過 |
| 純黑純白 | 明度直方圖 | 不用純黑純白（Dota、Ubisoft Fontan）；材質底色超出 sRGB 50–243 的像素 ≤ 2%（提案） |
| 色彩成群 | 飽和 > 0.15 的像素，依 12 格色相分組 | 前 3 格 ≥ 80%（提案；D4「colors need to group well」） |
| 語意色保留 | 保留給敵方、主角、掉落的色相在環境裡的佔比 | ≤ 1%（提案；Riot 敵我色票、Dota 避開地圖主色） |
| 材質底色 | G-buffer 的 base color | 非金屬 sRGB 50–243、金屬 180–255（DONTNOD、Unity、Adobe） |
| UI 字級 | 1080p 字高，量字形上伸到下伸 | PC ≥ 18 px、主機或電視 ≥ 26 px（XAG 101） |
| UI 對比 | 在背景對比最低處量 | 4.5:1；≥ 36 px 的大字 3:1（XAG 102） |
| 回饋延遲 | 60 fps 錄影，按鍵到可見變化 | ≤ 100 ms，約 6 幀（NN/g） |
| 閃光 | 最激烈的 60 秒片段 | 過 Harding FPA 或 PEAT（XAG 118） |
| 特效分級 | 各級的畫面佔比、峰值亮度、持續時間 | 由專案的分級表定（Riot 重要性階梯；數字是提案） |

## 4. 審查與回報

- **對照參考作品的同類鏡頭**（俯視混戰、首領登場、掉落、介面……），只寫公開看得到的鏡頭特徵，不附對方畫面。每段做成「項目｜我們｜差距」的表。
- 特效、角色這類用 Riot 式的正反例並排（ACCURATE／INACCURATE）。
- 回報附：同幀並排圖、數字前後、還差什麼；下一步依「最能拉近與參考作品的距離」排序。
- 沒有數字或並排圖的「看起來好多了」不算結論。

## 5. 研究新職能或補缺口

- 一個職能一路研究 agent，一次 2–3 路，每路寫明搜尋額度（約 40–50 次）。
- 問的是「這個職能的人怎麼做」：工具、流程、檢查標準、具名案例（GDC 講座、工作室部落格、官方文件、書）。
- 標【一手】【訪談】【二手】【學術】；查不到就列在「找不到」，不要編數字；業界沒有數字的門檻標「提案」。
- 原始回報先存在專案 `docs/`（例如 `docs/craft/_notes_<職能>.md`），整理成規則書的條目。
  **跨專案通用的方法回寫這個技能的參考檔**，專案專屬的參數與決定留在專案。
