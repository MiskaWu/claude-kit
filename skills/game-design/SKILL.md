# game-design —— 設計與審視玩法

從三路研究整理出來（2026-10-21）：經典框架（Schell、MDA、Koster、Cook……）、工作室公開的做法（Valve、Nintendo、Subset……）、
四類遊戲的經驗與反模式。原始筆記（附出處）在 [research/](research/)，平常不用讀。

**這裡只寫做法與檢查，不替專案決定玩法。** 體驗目標、🔒 設計意圖、生死判準是專案的答案，寫在專案的設計文件（第 0 節）。
網頁小遊戲的打磨迴圈與自動玩家人設在 game-polish；前搖、掉落看不看得見這類畫面問題在 game-art；推出去以後的事在 game-publish。

## 原則

- **好玩是一條鏈**：目標 → 決定 → 回饋（看得出、算數、能歸因）→ 學習 → 新挑戰。玩家只會說「不好玩」，你的工作是找出斷在哪一環。
- **設計是假設，試玩是實驗。** 設計者只改得到機制，體驗是規則跑起來之後長出來的（MDA）。每個原型寫清楚要回答的一個問題與生死判準。
- **Claude 量得到規則層，判斷不了好不好玩。** 主導策略、勝率、局長、運氣佔比用自動玩家量；會不會自己按再一局、輸了是笑是罵、
  說不說得出怎麼輸的，只有真人看得到。回報裡把兩者分開；沒有真人證據就寫「待試玩」，不寫「應該會好玩」。
- **你是沒有決定權的評論者。** 列斷點、證據、改法，拍板的是使用者。🔒 的設計意圖不動，要動就提出來讓他決定。
- **衝突先問定位，不給通用答案。** 隨機多少、失敗多痛、難度誰調，取決於這款要「可靠地量出誰最強」還是「讓每個人都有好的挑戰」，
  以及一局多長（Schell #37 #41）。專案沒寫就問。
- **標證據等級。** 引用時標【一手】【訪談】【二手】【學術】【推論】；把來源搬到這類遊戲的整合一律標【推論】。

## 0. 先找專案的設計文件

- 在專案 CLAUDE.md 找設計文件（設計憲法、SPEC、`docs/design.md`、`docs/decisions/`）。有就照它；跟這份技能衝突時以它為準。
- 沒有的話，照 [design-brief.md](design-brief.md) 建一份一頁設計與設計日誌，放在專案 `docs/`，在 CLAUDE.md 加一行指過去。
  **體驗那一句、支柱、定位、生死判準由使用者拍板**：你提選項與依據，問不到的留「未定」。
- 專案已經有自動玩家（game-polish 的規則層）、試玩網址、量測腳本，就用它，不另寫一套。

## 1. 設計：從點子到確定好玩

照 [references/process-and-playtest.md](references/process-and-playtest.md) 的七步：
寫成假設 → 玩具原型 → 剝掉外圍 → 觀察試玩 → 代表片段 → 量化 → 小規模公開。

- 每一步開工前，在設計日誌寫這一步要回答的問題與過關條件；做完記做了什麼、量到什麼、還差什麼。
- 使用者的試玩回饋照原話記進試玩筆記，不改寫成你的解讀；每個問題附一個提案。
- 生死判準沒過就停下來回報。不要繼續往上疊系統：核心還不好玩就加商店、每日、第二種貨幣，是最常見的反模式。
- 加新機制前，先說它落在鏈的哪一環、服務哪一個體驗目標；說不出來就先不加。

## 2. 審視：找斷點

1. 讀設計文件，有可玩版本就玩它。可玩版本優先：審的是玩起來的樣子，不是文件寫的樣子。
2. 寫一句「我以為這款要玩家感覺到什麼」，對照設計文件的體驗目標；對不上就是第一個發現。
   要新眼睛時，開一個沒有上下文的 subagent，只給一頁設計與可玩版，請它先寫這一句。
3. 沿著鏈走一遍（[references/fun-frameworks.md](references/fun-frameworks.md)），每一環判斷「成立／可疑／斷了」並附依據。
4. 可疑與斷掉的那幾環，把 [references/review-questions.md](references/review-questions.md) 對應的那一組問完；類型有參考檔的一起讀。
5. 掃一遍 [references/anti-patterns.md](references/anti-patterns.md)。
6. 量得到的就量（第 3 節），不只靠推理下結論。
7. 照第 4 節回報。

## 3. 量測

規則層用自動玩家量。專案有 game-polish 的規則層就沿用它的人設與固定種子；沒有的話照 game-polish 的 `rules-layer.md`
先把核心做成確定、可重播。設計層要多量的（做法在 decisions-and-balance.md）：

- **技巧天花板**：亂玩、簡單規則、搜尋或最佳化三種自動玩家的分數或勝率差。差太小代表決定不重要。
- **主導策略**：最佳化找到的策略是什麼、好不好玩、跟主題矛不矛盾。
- **運氣佔比**：同一策略換種子的變異。
- **選項死活**：選用率、有無勝率差；每個選擇點最佳與次佳選項的價值差。
- **對戰類**：勝率表附信賴區間、每格最佳回應、能動性指數、選型別的均衡、最懸殊的一格。
- **形狀**：局長、第一次失敗的時間點、強度曲線。

數字一律附：跑了幾局、幾個種子、哪一種自動玩家、指令。自動玩家是「一種玩家」，它的結果只說明規則層。

要使用者或親友試玩時，給一張看什麼的短清單（第一個輸入、失敗那一刻的反應、有沒有自己再來一局、說不說得出怎麼輸的），
不拿問卷判斷好不好玩。細節在 process-and-playtest.md。

## 4. 回報

審查的回報：

1. **一句話**：我以為這款要玩家感覺到什麼，跟設計目標對不對得上。
2. **鏈的狀態**：五環各一行，成立／可疑／斷了，附依據。
3. **發現**，依嚴重度排。每條寫：
   - 斷點：哪一環、哪個機制。
   - 證據：設計文件的哪一段、量到的數字、試玩觀察；沒有證據的標【推論】。
   - 嚴重度：**擋路**（核心體驗不成立）／**削弱**（體驗打折）／**打磨**。
   - 改法：一到兩個選項，附出處或類比；會動到 🔒 意圖的寫明，交給使用者。
   - 要真人驗的是什麼。
4. **量了什麼、沒量什麼**：指令、局數、種子；量不到的列出來。
5. **待拍板**：定位問題（量技巧還是共享體驗、一局多長、失敗多痛）與改法的選擇。

設計工作的回報：這一步回答了哪個問題、生死判準過了沒、設計日誌追加了哪一條。

玩法的問題也照全域「修 BUG 先想設計」：先分辨是參數沒調好，還是模型或結構缺了一項（例如某個參數只有好處沒有代價，必然主導）。
掃遍參數空間都到不了目標，就是結構問題，提重新設計的選項，不要用特例分支繞過去。

## 5. 補研究

平常不重跑研究。碰到參考檔沒涵蓋的類型或題目（研究文件 §11 列了這輪的缺口），才補那一塊：

- 一次派 2–3 路研究 agent，每路寫明搜尋額度（約 40–45 次）。問的是「做這類遊戲的設計師怎麼做」：具名案例、流程、能量的檢查。
- 標【一手】【訪談】【二手】【學術】【推論】；查不到就列「找不到」，不編數字、不編演講標題。
- 原始筆記放 `research/`；跨專案通用的做法回寫對應的參考檔，專案專屬的決定留在專案。
- 好讀版有改，用同一個檔案重發到同一個網址。
