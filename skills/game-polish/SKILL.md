# game-polish —— 網頁小遊戲的打磨

從三款網頁小遊戲（物理動作、限時判斷、即時行情）的打磨帶出來的做法（2026-10）。
使用者通常只給方向（「打磨到可以比評鑑上高分的遊戲」），每一輪照下面的迴圈自己找問題、自己驗證，最後由他用手機試玩一句話判定。
**這裡只寫做法，不替專案下結論**：每個專案照第 1 節巡一遍，列出自己的落差清單；這個專案做了什麼記在它自己的決策文件。
畫面上的落差（配色、燈光、特效、UI/UX、美術規則書）照 game-art 技能裡各職能的方法修，不憑感覺調。

## 0. 先看專案有沒有現成的

開工前在專案的 CLAUDE.md、`docs/decisions/` 找「打磨」：有的話照它指的巡覽腳本、玩家模型、試玩網址走，不要另寫一份。
沒有就照第 1 節做，做完把巡覽腳本收進專案（例如 `web/scripts/tour.mjs`），在專案 CLAUDE.md 加一行指回這個技能和腳本位置。

## 1. 每一輪的迴圈：截圖 → 對標 → 修 → 再截同一組

不要憑印象改畫面。每一輪：

1. **建置**，包含使用者手機上玩的那一版（通常是 claude.ai Artifact 的單檔版）。
2. **規則層**（遊戲核心是確定性、可重播的才做）：用自動玩家跑一批固定種子，量指標，依數據調參；底線寫成測試。見 [rules-layer.md](rules-layer.md)。
3. **畫面層**：無頭瀏覽器巡過每個畫面、逐張截圖，同時收 `pageerror` 與 `console.error`（有就先修）。
   範本在 [templates/](templates/)：`tour.cjs`（全部畫面）、`scenario.cjs`（固定一個情境，截事件發生那一刻與之後）、
   `seed-state.cjs`（載入前塞好存檔狀態）、`artifact-smoke.cjs`（單檔版開得起來、沒有錯誤）。
   尺寸至少三種：手機直放 390×844、手機橫放 844×390（`isMobile`、`hasTouch`、`deviceScaleFactor: 2`）、桌機 1280×720；
   多語系的遊戲每個語系跑一次。截圖照輪次命名 `r0-…`、`r1-…`，前後才比得出差別。
4. **讀截圖自評**，照 [checklist.md](checklist.md) 列出落差、照影響排序，挑影響最大的幾項改。
5. **改完重截同一組**，比前後；跑全套測試。
6. **交付**（見第 3 節），等使用者一句話。他的短回饋（「配色太少」「歪得有多爛也很重要」）同時是需求和方向：
   做完那一項，順著同一個方向再看一遍還缺什麼。

截圖巡覽會抓到真的 bug，不只是美觀：「預覽畫布蓋住所有按鈕」「點了開始之後空白鍵沒反應」都是巡覽腳本點不到按鈕（逾時）時抓到的，
單元測試抓不到。**腳本點不到東西本身就是 bug 訊號。**

## 2. 結構原則：打磨不能把語意弄岔

畫面一加料，最容易「畫面說一套、系統做另一套」：

- **畫面＝系統實際發生的事。** 按鈕亮＝這一步真的在作動（讀遊戲狀態，不讀手指有沒有按著）；回放與示範時照樣會亮。
  飛出去的零件照核心算出的清單噴，車上少掉的就是飛出去的那顆。
- **特效只對事件反應。** 事件由主迴圈比對前後兩步的狀態差產生；畫面與音效層永遠不寫遊戲狀態。
- **回饋不動判定與計分。** 連對、音效、閃光、進度條都只讀狀態；計分與重播只有核心一份（伺服器重播的遊戲尤其要守）。
- **慢動作只改每秒跑幾個固定步，不改步長**，結果照樣可以重播。
- **可調的東西放進表裡**（配色、門檻、裝置、評語），迭代時加一列，不在各處寫分支。
- **分數門檻先捨入再查表**；寫一條「剛好在門檻上」的測試（浮點相加的滿分可能是 99.99999999999999）。
- 專案的 SPEC 有標「不可動」的設計意圖就不碰；調了玩法要回寫 SPEC 或決策文件。

## 3. 交付與收尾

- 全套測試（照專案 CI 的指令）→ 重截那一組 → 發佈到**同一個**試玩網址 → 附 2～3 張代表截圖（SendUserFile）。
- **寫清楚沒驗到的**：音效好不好聽、音量、真機效能、真機手感與震動、「第一次點下去才出聲」順不順——無頭瀏覽器都驗不到。
- 這一輪做了什麼、每輪抓到哪些落差，寫進專案的決策文件（例如「打磨：手感與心流」一篇），不要只留在對話裡。
- 巡覽與玩家模型的腳本收進專案；一次性的放 scratchpad 會隨對話消失。

坑與解法見 [pitfalls.md](pitfalls.md)：開工前掃一遍，踩到新的就補進去。
